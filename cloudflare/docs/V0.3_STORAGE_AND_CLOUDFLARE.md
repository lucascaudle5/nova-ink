# NOVA Ink v0.3 — storage design and Cloudflare backend

Status: **design + local spike.** Nothing here has been deployed or run on Cloudflare infrastructure. Every "measured" number below came from local workerd (Miniflare) on a Windows PC with generated test data, and is labelled as such. Items that only a real deployment can answer are in [section 9](#9-open-questions-that-need-a-real-deployment).

**Update (Oct 29, 2026):** the auth layer (section 7) and an MCP layer now exist in code and in local tests, and a throwaway test deployment is prepared; see [CF_TEST_DEPLOYMENT.md](CF_TEST_DEPLOYMENT.md) for what is verified and what is not. Nothing has been verified on real Cloudflare yet: the first-spike JSON API described as "no authentication" below was removed.

The v0.2.x Windows server remains the working version until a Cloudflare version passes equivalent tests. This spike covers one part of that: the per-canvas storage engine and the save protocol. It is not an MCP server yet and has no authentication.

---

## 1. What the spike proves, and what it does not

Built and tested locally (`npm test`, `npm run test:node`; results in the report and in `docs/bench-results.json`):

- One SQLite-backed Durable Object (`CanvasDO`) per canvas, with tldraw records stored as rows.
- A change-based save protocol (put/remove records against a base revision, with `saveId`) that keeps the v0.2 invariants.
- Images stored once, content-addressed, in chunks under the 2 MB row limit.
- Checkpoints (gzip, chunked) for history and recovery; restore as a new revision.
- A read-only, idempotent importer for v0.2.x data directories.

Not built (listed so nothing is assumed to exist): Library object (notebooks/pages/trash), authentication, the MCP layer on Workers, paged load/save, alarm-based checkpoints, tiered checkpoint retention, "start fresh" for an unrecoverable canvas, staged bulk import, the host adapter code, any UI change.

## 2. v0.3 data model

### 2.1 Entities

```
User (one, but modelled so it could be more)
 └─ Library            1 Durable Object per user ("library:<userId>")
     ├─ notebooks      id, name, sort_key, created_at, updated_at, deleted_at?, schema_ver
     ├─ pages          id, notebook_id, canvas_id, title, sort_key (fractional index),
     │                 kind ('ink' | 'pdf'), source_id?, source_page?, source_meta (JSON)?,
     │                 created_at, updated_at (coarse), deleted_at?, saved_once, meta (JSON)
     └─ sources        id, kind ('pdf'), sha256, filename, byte_size, page_count, imported_at,
                       store ('r2' | 'blob'), store_key, deleted_at?   (see 2.2)
 └─ Canvas             1 Durable Object per page document ("canvas:<canvasId>")  ← built in the spike
     ├─ records        one row per tldraw record (shape / page / binding / asset / document)
     ├─ kv             head, schema, session, lease
     ├─ blob_index + blobs         image payloads, content-addressed, chunked
     └─ checkpoint_index + checkpoint_chunks   gzip'd full-document history
```

- **Notebook** = a named, ordered collection of pages. **Page** = one tldraw document. A v0.2 "canvas" is exactly a v0.3 page.
- **Ordered pages**: `sort_key` is a fractional index (same idea tldraw uses for shape order). Reordering rewrites one row, not the list.
- **Page metadata** (title, tags, free-form `meta`) lives in the Library, not in the canvas object, so listing a notebook never wakes canvas objects.
- **Soft delete / trash**: deleting a notebook or page sets `deleted_at`. Trash lists rows with `deleted_at` set; restore clears it. A Library alarm purges items older than 30 days by calling `deleteAll()` on the canvas object and removing the row. Nothing is destroyed at delete time.
- **Schema versioning, three levels**, all refuse-rather-than-guess like v0.2's `MANIFEST_NEWER`:
  1. `head.format` per canvas object (spike: `FORMAT_VERSION = 1`; a newer value returns `FORMAT_NEWER`, tested).
  2. `schema_ver` in the Library.
  3. tldraw's own `document.schema`, stored verbatim; the client's `loadSnapshot` runs tldraw's migrations, and the widget already refuses to mount a snapshot it cannot load.
- **Image assets stored once**: the asset record keeps `props.src = "nova-blob:<sha256>"`; the payload lives once in `blobs`, keyed by hash, shared by every asset record and every checkpoint in that canvas. Garbage collection removes a payload only when no live record and no retained checkpoint refers to it (tested). Dedupe is per canvas; cross-canvas dedupe would need a shared store (R2, section 5.4).

### 2.2 Imported PDF pages and source provenance (next feature after acceptance; model only, nothing built)

An imported PDF page is an ordinary page whose canvas has a locked background image, so every guarantee above (revisions, lease, checkpoints, recovery) applies to it unchanged. What is added is **provenance**, kept in the Library so it never touches the canvas save path.

- **`pages.kind`**: `'ink'` (default; every v0.2 page) or `'pdf'`. Unknown future kinds are shown read-only rather than guessed at, same refuse-don't-guess rule as schema versions.
- **`sources`** (one row per imported file, shared by all its pages): `sha256` of the original PDF bytes, original `filename`, `byte_size`, `page_count`, `imported_at`, and where the original lives (`store` + `store_key`). Importing the same file twice finds the same `sha256` and reuses the source row.
- **Per page**: `source_id`, `source_page` (1-based page number in the PDF), and `source_meta` JSON recording how the background was produced: `{ pageWidthPt, pageHeightPt, rotation, renderer: "pdfjs@<version>", scale, renderedAt, backgroundSha256 }`. This lets a page be re-rendered later (new renderer, higher DPI) without losing annotations, because the strokes are separate records.
- **Canvas side**: the rendered page is one `asset` record plus one locked `image` shape, stored through the existing content-addressed blob path (so it is stored once and chunked under 2 MB). The shape and asset carry `meta: { novaSource: { sourceId, page } }`, a small self-describing back-reference so a canvas exported or recovered on its own still says where it came from. tldraw preserves record `meta`, and the spike stores records verbatim, so no engine change is needed. Student ink strokes are normal shapes above it; they are never merged into the background, which keeps "what the PDF said" and "what I wrote" distinguishable (and keeps independent work separable from imported material).
- **The original PDF is not stored in a canvas object.** A multi-MB PDF in SQLite rows would eat chunk rows and storage against the 1 GB per-object free limit. Recommended: R2 (free tier verified in section 5.3), keyed by `sha256`; fallback if R2 is not available: chunked `blob` storage in a dedicated Sources object. Rendering happens in the client (pdf.js), so no PDF parsing CPU is spent in a Worker.
- **Delete semantics**: deleting a page never deletes the source. A source is purged only when no non-trashed page references it, and only by the same 30-day trash rule.
- **Reordering / extracting**: pages from one PDF can be reordered, moved between notebooks or deleted independently; provenance travels with the page row. Importing a page range creates only those pages, and `page_count` still records the full file.
- **Migration impact**: none. All v0.2 and imported pages become `kind = 'ink'`, `source_id = NULL`. Fields are additive and optional (AGENTS.md: backward compatible, no silent migrations). The v0.2 importer's `library[]` output would simply omit them.
- **Budget impact**: a background image is a one-time blob write (roughly 18–23 rows for a 3–8 MB render, measured for image canvases); the page-row and source-row writes are in the Library. A 40-page PDF at one image per page is about 40 canvases created, so spread the import or batch it (same guidance as section 6).
- **Open questions** (need real use, not this spike): render resolution vs the 12 MiB / CPU limits on iPad; whether to keep pre-rendered backgrounds at all or re-render on demand from R2; PDF files with forms, annotations or encryption; privacy of source files (they are only in your R2 bucket).

### 2.3 Why one Durable Object per canvas (not per notebook)

| | Per canvas (chosen) | Per notebook |
|---|---|---|
| Matches v0.2 semantics | Yes: lease, revision and conflict are already per canvas | Would need per-page revisions inside one object |
| Load cost | Proportional to the one page being opened | Must not load other pages; needs paging logic anyway |
| Contention | Saving page A never queues behind page B | One single-threaded object serialises every page |
| Failure blast radius | One damaged canvas affects one page | One bad row set can affect a whole notebook |
| Storage ceiling | Free plan: **1 GB per object** (see 3.2); a page rarely nears it | A heavy notebook could hit it |
| Cost of listing / reordering | Needs the Library object (one extra object) | Free (same object) |

The extra Library object is the price. It is small (hundreds of rows) and writes rarely, if updates to it are debounced (section 3.3).

## 3. How it maps onto Durable Objects, SQLite and the limits

### 3.1 Limits that shaped the design

| Limit (Cloudflare docs, Oct 2026) | Design response |
|---|---|
| 2 MB per row/value/BLOB | Records kept < 1.9 MB (`RECORD_TOO_LARGE` otherwise); image payloads and checkpoints in 1,000,000-byte chunks. Spike test checks every chunk and record is under the limit. |
| 100,000 rows written/day | One row per changed record; unchanged records are not rewritten; no per-save history rows. See measurements. |
| 5M rows read/day | A save reads ~3–4 rows; a load reads N+few. Not a constraint at personal scale. |
| 100 bound params, 100 KB statements | Row-at-a-time statements with bound values; image data is bound, not inlined in SQL text. |
| 10 ms CPU per Workers request | **The big risk** — see 3.4. |
| Free DO storage 5 GB per account; **1 GB per object** (the limits page says "10 GB on Workers Paid, or 1 GB on the Free plan") | Fine for personal notes; images are the only way to approach it. |

### 3.2 Table design

All tables are `WITHOUT ROWID`. A normal rowid table with a TEXT primary key writes an extra index row per insert, which would double the billed row writes. The spike's local counter agrees with one billed row per logical row: a first save of a 1,502-record canvas wrote 1,506 rows (records + head + schema + session + lease).

### 3.3 Save protocol (what the client sends and what the object does)

Request: `{ clientId, saveId, baseRevision, puts[], removes[], session?, schema? }`. `session` and `schema` are omitted when unchanged.

Order of checks, deliberately the same as v0.2 `storage.mjs`:

1. **Replay**: if `head.saveId === saveId && head.savedBy === clientId` → `{ ok, replayed: true }`, **0 rows written** (tested).
2. **Lease**: held by another client and unexpired → `LEASE_HELD`.
3. **Revision**: `baseRevision !== head.revision` → `CONFLICT { revision, ownLastSaveId }`. `ownLastSaveId` is non-null only when *this client* made the last save, so a client can tell a lost acknowledgement from a real conflict (both cases tested).
4. Validate (record shape, size limits). Externalise images to `blobs`.
5. Compute the *effective* change set: puts identical to the stored row are dropped; removes of absent ids are dropped. This reduces row writes and defines "the document actually changed".
6. If the document changed and a checkpoint is due, write a checkpoint of the **prior** revision **before** the commit point (same as v0.2 backups; a failure here leaves the previous revision intact).
7. **Commit point**: one `transactionSync` writing blobs, records, deletes, schema/session and the `head` row (new revision, `saveId`, `savedBy`, `savedAt`, `recordCount`). Atomic: a trigger-induced failure mid-transaction rolled everything back in a test; a fault injected before the commit leaves the old revision (tested).
8. **After the commit point**: lease renewal, checkpoint pruning, blob GC. Failure here returns `ok: true` with a `warning` (tested). A storage exception before the commit is returned as `STORAGE_ERROR`, never thrown, and never half-applied.

Revision increments on every save, including camera-only saves, as in v0.2. Checkpoints are written only when the document changed.

**Lease**: 45 s, in memory, with a persisted copy written **only when the holder changes** (acquire by a different client, take-over, release). Heartbeats (every 15 s) write 0 rows. If the object is evicted and restarted it reads the persisted lease, so a second client is still read-only (tested across a real process restart). Open question: how often free-plan objects are evicted between 15 s heartbeats (section 9).

**Loading**: `open` returns the full snapshot reassembled from rows, with corrupt/missing detection (below). `openRaw` returns the finished JSON text by concatenating stored row JSON without parsing it, with cheap integrity checks; a damaged row that still looks like an object makes the client's `JSON.parse` throw, and the client must treat that as `CORRUPT_RECORD`. Both return the same document in tests (including a chunked 3 MB image). Measured benefit of `openRaw` was modest (below), so it is an option, not a fix.

**Corrupt / missing** (`CORRUPT_RECORD`, `MISSING_RECORD`), tested:
- unreadable `head` → corrupt; head missing but the Library says the page was saved (`knownRevision > 0`), or checkpoints/records exist → missing; fewer rows than `head.recordCount` → missing; an unparseable record row → corrupt.
- A missing record is never treated as a blank canvas.
- Restore from a checkpoint creates a **new** revision (never reuses a number a client may hold, tested: `knownRevision` and the raw head's revision both feed the next number), checkpoints the current state first, or copies a damaged state into `quarantine` rows (tested).
- Known gap vs v0.2: record-level damage is detected on **open**, not on every save (a save does not read every row). Clients always open before saving, but this is a difference.

**Library write debouncing** (not built): updating `pages.updated_at/revision` on every save would add 1 row write per save (~20–25% more). Instead the Library stores `saved_once` (for the `knownRevision > 0` check) and a coarse `updated_at` refreshed at most every few minutes and on lease release.

### 3.4 CPU: what we know and what we do not

Measured **locally** (CPU time of the workerd process, per request, includes HTTP/JSON handling; this PC's CPU, not Cloudflare's; there is a ~3–5 ms per-request floor visible in `heartbeat`):

| Operation | CPU ms (this PC) |
|---|---|
| heartbeat (no-op) | 3–5 |
| typical save, +3 strokes on a 1,500-stroke canvas | 5–8 |
| camera-only save | 4–7 |
| open, 100 strokes (0.13 MiB) | 8–14 |
| open, 500 strokes (0.65 MiB) | 40–60 |
| open, 1,500 strokes (1.95 MiB) | 140–300 |
| open, 3,000 strokes (3.9 MiB) | 320–430 |
| first/full save, 1,500 strokes | 240–360 |
| checkpoint write (gzip), 1,500 strokes | ~140–160 |

Reading this honestly:
- **If the free-plan 10 ms Workers CPU limit applies to Durable Object requests**, typical small saves fit (marginally); **loading, bulk saves and checkpoints of anything beyond ~100 strokes do not.**
- If free-plan objects get the 30 s default, none of this matters.
- Cloudflare CPU time excludes I/O waits and runs on different hardware; the local figure is a relative guide only.

Mitigations, in order of preference if the limit is 10 ms (all unbuilt): (1) **paged load and bulk save** — pages of ≤ ~50 records per request, with the revision re-checked per page; request count is not the constraint (100k requests/day); (2) **alarm-based checkpoints** run after a quiet period instead of inside a save; (3) Workers Paid plan for the CPU limit; (4) keep the Windows server as the primary. Decide after the one-hour deployment test in section 9.

## 4. Measurements: row writes and the daily budget

Local counters from SQLite inside the object (`rowsWritten`), generated data, real tldraw snapshots (`docs/bench-results.json`):

| Save | Rows written |
|---|---|
| +3 new strokes on a 1,500-stroke canvas (session unchanged) | **4** (3 records + head) |
| same, with session changing (typical in real use: camera/selection) | **5** (adds the session row) |
| camera-only save | 2 (session + head) |
| replayed save (lost-ack retry) | 0 |
| heartbeat | 0 |
| open (lease holder changes) | 1 |
| full first save, N records | N + 4 (1,506 for 1,500 strokes) |
| first save of a 3 MB image canvas | 18 (4 blob chunks + index + records + head…) |
| first save of an 8 MB image canvas | 23 |
| checkpoint | 2 rows for a 1,500-stroke canvas (1 chunk + 1 index) |

**Saves per day inside 100,000 rows written**

| Assumption | Saves/day |
|---|---|
| 5 rows per save | **20,000** |
| 4 rows per save | 25,000 |
| camera-only (2 rows) | 50,000 |
| plus checkpoints (≤144/day at one per 10 min, ~2–4 rows each) | −~0.5% |
| A whole-canvas save of 1,500 strokes (1,506 rows) | ~66/day if that were *every* save |

At one autosave per 3 s of continuous writing (20 saves/min) the 20,000-save budget lasts ~16 hours of nonstop writing. The budget is shared across **all** objects in the account, so the Library, imports and any other canvas count against the same 100k. Importing a whole v0.2 library costs about one row per record (10 canvases × 1,500 strokes ≈ 15,000 rows), so spread large imports over days or do them in pieces.

## 5. Backup and revision history that does not blow the row-write budget

### 5.1 Recommendation

**In-object gzip checkpoints, rate-limited, with R2 as an optional off-site copy.**

- A checkpoint is the whole document (records + schema + session) as one gzip blob split into ≤ 1,000,000-byte chunks. Rows written = chunks + 1, **independent of how many records the canvas has**. A 1,500-stroke canvas compresses from ~2 MB to ~0.28 MB: 2 rows.
- Rate limit: at most one per 10 minutes, and only when the document changed (camera-only saves never trigger one). Keep the newest 10 (parity with v0.2's `BACKUP_COUNT`).
- Referenced images are *not* copied into checkpoints (they hold `nova-blob:` refs), so a checkpoint of an image-heavy canvas stays small; GC keeps referenced payloads alive.
- Restore creates a new revision and checkpoints the current state first.

Why not the alternatives:
- *Row-per-record version history / per-save journals*: +1 or more rows on every save, roughly +20–100% of the daily row budget.
- *Checkpoint on every save*: removes the point of change-based saves and costs CPU (gzip ≈ 140 ms locally for 1,500 strokes).

### 5.2 Weaknesses to accept or fix

- **Retention is short in time.** 10 checkpoints at ≥ 10 minutes covers ~100 minutes of active editing, not days. Recommended (unbuilt): tiered retention — newest 5, plus one per day for 14 days, plus one per week for 8 weeks. Row cost is still 2–3 rows per checkpoint.
- **The checkpoint is in the same object as the data.** A deleted object loses its history. Hence R2 below.
- **Checkpoint CPU** is inside a save in the spike (parity with v0.2). Move it to an alarm if the CPU limit turns out to be 10 ms.

### 5.3 R2 (optional, off-site)

Verified in the Cloudflare R2 pricing page (updated Oct 26, 2026): free tier is **10 GB-month storage, 1 million Class A operations/month, 10 million Class B operations/month**, egress free, delete free. A daily-or-periodic `PutObject` per canvas is a few thousand Class A operations a month, far inside the free tier. R2 is justified only for protection against losing the Durable Object itself (accidental `deleteAll`, a bug, a bad migration) and for cheap long-term archives. Not verified, so check before relying on it: whether enabling R2 requires a payment method on file even for the free tier.

### 5.4 Cross-canvas image dedupe

If the same image is pasted into many canvases, R2 (content-addressed by hash) would store it once for all. Not needed for v0.3 launch.

## 6. Migrating v0.2.x data (non-destructive, tested)

Source layout: `manifest.json` (version 1), `canvases/<uuid>.json` (`{revision, snapshot, saveId, savedBy, savedAt, meta}`), `backups/<uuid>-<rev>.json`.

Implemented in `src/import-v02.mjs`, tested in `test/node/node.test.mjs` with a generated v0.2 directory:

1. **`readV02(dir)`** only reads. A test hashes the whole source tree before and after and requires the hashes to be equal. It reports problems (damaged canvas file, bad backup) instead of repairing them. It refuses a manifest from a newer version. Canvases or backups with no manifest entry are listed as "Recovered canvas …" (same as v0.2 orphan handling).
2. **`applyImport(plan, api)`** writes into a **fresh** store via the normal API, preserving canvas ids and revisions (`importedRevision`), importing backups as checkpoints at their original revision numbers, and releasing the importer's lease. Running it twice is safe (`saveId = import-<canvasId>` replays).
3. A canvas whose current file was damaged but which has backups imports its backups only; it then opens as `MISSING_RECORD` and restores from the imported backup, exactly like v0.2 (tested, with a revision that does not collide with the old number).
4. Never-saved (revision 0) canvases create only a Library entry.

Mapping to v0.3: each v0.2 canvas becomes a **page**; put them all in one notebook, "Imported from v0.2", ordered by the manifest. `applyImport` returns the `library[]` entries (id, name, createdAt, revision, status) the Library object should record.

Real-use procedure (only after the account exists and the CPU question is answered):
1. Stop editing in v0.2 (or accept that later edits are not copied). Run `npm run backup` in the NOVA repo first.
2. Run the importer against the **deployed** Worker with a one-off token. Source is only read.
3. Compare per canvas: record count, `JSON.stringify` equality of snapshots, image bytes. Open each in the new UI.
4. Keep the Windows server and its data untouched until you have used v0.3 for a while.

Not built: **staged bulk import.** A 1,500-stroke canvas in one request cost ~240 ms CPU locally; if the limit is 10 ms the importer must send ≤ ~50 records per request into a staging area and flip the canvas live with one final commit.

## 7. Auth design: Cloudflare Access + Workers OAuth Provider

Verified against current docs ("Authorization" in Cloudflare Agents docs, updated Oct 27, 2026; "Secure MCP servers", Cloudflare One docs, updated Oct 22, 2026). Not run.

### 7.1 For ChatGPT (MCP over OAuth)

Two roles (from the docs):
- **Authorization server**: `OAuthAuthorizationServer` from `@cloudflare/workers-oauth-provider`. Serves discovery, client registration (`clientIdMetadataDocumentEnabled`, optional `/oauth/register`), and the token endpoint. `scopesSupported: ["mcp:read","mcp:write","offline_access"]` — `offline_access` is what gives ChatGPT refresh tokens. Needs a KV namespace `OAUTH_KV` and the `global_fetch_strictly_public` compatibility flag. **The `/authorize` page is ours**: it signs the user in, asks consent, then calls `completeAuthorization()` with `props: { userId }`.
- **Resource server**: the MCP Worker, `OAuthResourceServer` around `createMcpHandler`. It publishes protected-resource metadata, returns 401 without a valid token, rejects tokens for other resources, and checks tokens through a Service Binding to the authorization server. Tools read `props` via `getMcpAuthContext()`.

Sign-in at `/authorize` uses **Cloudflare Access for SaaS (OIDC)**: create a SaaS application with OIDC, redirect URL = our Worker's `/callback`, turn on **Refresh tokens** (docs mention 90 d lifetime in the API example), add one Access policy allowing only your email. The Worker acts as an OIDC client of Access (client id/secret, token/authorization/jwks endpoints, from the dashboard) and, after the callback, maps the verified `sub`/`email` to `userId` and calls `completeAuthorization()`. The documented reference is the `remote-mcp-cf-access` template.

Allowlist: policy "Emails = <your address>" in Access, and also check `email` in our `/callback` (defence in depth).

Scope use: `mcp:read` for open/list; `mcp:write` for save/restore/import. The widget-only tools stay `visibility: ["app"]` as today.

### 7.2 For the standalone browser mode

The same Worker (or a sibling) serves the web UI. Protect it with an Access **self-hosted application** so the browser gets a `CF_Authorization` cookie; the Worker validates the `Cf-Access-Jwt-Assertion` header against the team's JWKS and the application's AUD tag, then derives the same `userId` from the email. No OAuth is needed in this path.

Both paths yield the same `userId`, so both open the same Library object.

Caveats to verify at deployment: whether the Access application and the OAuth/MCP paths can share a hostname (the MCP path must bypass the Access login and use OAuth tokens instead), or whether it is simpler to use two Workers/hostnames; and whether an Access self-hosted application needs a domain on your Cloudflare account or can protect `*.workers.dev`.

### 7.3 Rules regardless of path

- Every request resolves `userId` before choosing a Library/Canvas object name; object names are `"library:<userId>"` and canvas ids are checked to belong to that Library. The spike has none of this and **must not be deployed as is**.
- Never log tokens or `props`. Secrets via `wrangler secret put`, never in the repo.

## 8. Host adapter: one UI, two hosts

The shared UI already talks to storage through a single function type in `src/session.ts`: `Api = (name, args) => Promise<ApiData>`. Make that the formal host adapter:

```ts
interface HostAdapter {
  call(op: SaveOp, args: object): Promise<ApiData>   // open, save, heartbeat, release, list, restore, saveAsNew…
  clientId(): string                                  // persisted per device/tab
  theme(): 'light' | 'dark'
  onVisibility(cb: (visible: boolean) => void): void  // flush saves on hide / close
  capabilities: { sidePane: boolean; offlineDrafts: boolean; openLink(url: string): void }
}
```

- **ChatGPT MCP App adapter**: `call` → `app.callServerTool({ name: 'ink_<op>', arguments })` via `@modelcontextprotocol/ext-apps`; capabilities as today.
- **Standalone adapter**: `call` → `fetch('/api/canvas/:id/:op')` with the Access cookie; same JSON replies, so `session.ts` does not change.
- Everything above the adapter (session controller, editor, conflict handling, recovery UI) is shared and keeps its existing test suite; the standalone adapter is tested by running the same session tests against it.
- `ApiData` gains optional fields only (backward compatible), per AGENTS.md.

The spike's protocol (changes against a base revision) needs one client-side addition: a small module keeping the last acknowledged snapshot and calling `diffSnapshots` (`src/diff.ts`). `session.ts` currently sends whole snapshots; that is the only behavioural change.

## 9. Open questions that need a real deployment

Cannot be answered locally; each has a concrete test.

1. **CPU limit for free-plan Durable Objects.** The limits page says "Durable Objects are Worker scripts, and have the same per invocation CPU limits as any Workers do" and also "default 30 seconds". Test: deploy `CanvasDO`, load/save the 1,500-stroke fixture, watch for `exceededCpu`/error 1102 and look at CPU time in the dashboard logs.
2. **Real CPU time** of typical save, load and checkpoint (local numbers are relative only).
3. **Access + ChatGPT OAuth flow**: does ChatGPT complete discovery → `/authorize` → Access login → callback → token → refresh? Does it keep a session across days without re-authorizing? What does `offline_access` actually produce? Where does ChatGPT show errors?
4. **Latency** from the iPad and the PC: time for open and for an autosave round trip, and where Cloudflare places the object relative to you.
5. **Row-write accounting** on real infrastructure: confirm the dashboard counts match the local `rowsWritten` (1 per logical row).
6. **Object eviction vs 15 s heartbeats**: does the object stay in memory between heartbeats, and does a persisted-only-on-change lease behave?
7. **Payload limits through ChatGPT**: the largest tool-call argument/response the widget bridge accepts (v0.2 sends up to 12 MiB through the tunnel today).
8. **Access details**: shared hostname vs two hostnames; domain requirement; refresh-token lifetime behaviour; whether the free Zero Trust plan is sufficient (stated to be free for small teams, but not verified here).
9. **`CompressionStream` cost** and behaviour in the production runtime.
10. **KV limits** for `OAUTH_KV` on the free plan (small, but unverified here).
11. **R2 sign-up requirements** on the free tier.

Treat items 1, 3 and 7 as go/no-go for moving off the Windows server.

## 10. What you must do to set up the account and Access

Do these yourself; the spike does none of them. Nothing in the repo logs in or deploys.

1. **Create a Cloudflare account** (free plan) at dash.cloudflare.com. Use a strong password and turn on two-factor authentication.
2. **Install and sign in with Wrangler** (only after step 1): in `nova-ink-cloudflare-spike`, `npx wrangler login` opens a browser for OAuth. Check with `npx wrangler whoami`. Stop here until we have agreed what to deploy first.
3. **Set up Zero Trust**: dashboard → Zero Trust; choose a team name (this becomes `<team>.cloudflareaccess.com`) and the free plan. Add **One-time PIN** as an identity provider (or Google/GitHub if you prefer).
4. **Create an Access policy** `NOVA owner`: Allow → Emails → your own address only.
5. **Create the Access for SaaS application** (OIDC): Zero Trust → Access controls → Applications → Create → SaaS → OIDC. Redirect URL = `https://<worker>/callback` (known only after the first deploy). Turn on **Refresh tokens**. Attach the `NOVA owner` policy. Copy client id, client secret, token / authorization / key endpoints.
6. **Create the KV namespace**: `npx wrangler kv namespace create OAUTH_KV`.
7. **Store secrets** (never in git): `npx wrangler secret put ACCESS_CLIENT_ID`, `ACCESS_CLIENT_SECRET`, `ACCESS_TOKEN_URL`, `ACCESS_AUTHORIZATION_URL`, `ACCESS_JWKS_URL`, and `COOKIE_ENCRYPTION_KEY` (a random 64-hex-character string).
8. **First deployment test (step 1 of the go/no-go)**: deploy only a throwaway version of this spike with auth in front, run the CPU/latency checks from section 9, then delete it.
9. **Standalone mode (later)**: add a self-hosted Access application for the UI hostname with the same policy.
10. Only after the equivalent test suite passes against the deployed Worker, run the importer (section 6) and keep the Windows server in place in parallel.
